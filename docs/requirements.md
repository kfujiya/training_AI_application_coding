# Requirements

## 1. 概要

タスク管理を目的としたWebアプリケーションを開発する。

ユーザーがログインし、自分のタスクを登録・編集・削除・検索できるようにする。

タスクにはステータス、優先度、期限、タグを設定できるようにする。

将来的にはSlack APIなどの外部APIと連携し、タスクの通知機能を追加できる構成とする。

---

# 2. 目的

本アプリケーションの開発を通して、以下の技術要素を扱うことを目的とする。

* JavaによるWebアプリケーション開発
* Spring Boot
* Spring MVC
* Spring Security
* Thymeleaf
* Spring Data JPA
* PostgreSQL
* REST API
* 外部API連携
* 認証・認可
* DB設計およびリレーション管理

---

# 3. 技術構成

初期バージョンでは以下の技術を使用する。

| 分類         | 技術                          |
| ---------- | --------------------------- |
| 言語         | Java 21                     |
| ビルドツール     | Maven                       |
| Webフレームワーク | Spring Boot                 |

# 4. ユーザー

## 4.1 ユーザー登録

ユーザーはアカウントを登録できる。

登録時に以下の情報を入力する。

* ユーザー名
* メールアドレス
* パスワード
* 表示名

### 入力制約

* ユーザー名は必須とする。
* メールアドレスは必須とする。
* パスワードは必須とする。
* 表示名は必須とする。
* ユーザー名は重複不可とする。
* メールアドレスは重複不可とする。
* パスワードは平文で保存しない。

パスワードはSpring Securityで使用する適切なPasswordEncoderを利用してハッシュ化して保存する。

---

# 5. 認証

## 5.1 ログイン

登録済みユーザーはメールアドレスとパスワードを使用してログインできる。

認証処理にはSpring Securityを使用する。

## 5.2 ログアウト

ログイン中のユーザーはログアウトできる。

ログアウト後はログイン画面へ遷移する。

## 5.3 未認証ユーザー

未認証ユーザーが認証必須の画面へアクセスした場合、ログイン画面へ遷移させる。

タスク管理機能はログインユーザーのみ利用できる。

---

# 6. 認可

タスクおよびタグはユーザー単位で管理する。

ユーザーは自分が所有するタスクおよびタグのみ操作できる。

他ユーザーのタスクやタグについて、以下の操作を禁止する。

* 閲覧
* 登録
* 更新
* 削除

URLのパラメータなどを直接変更した場合でも、他ユーザーのデータへアクセスできないようにする。

認証済みであることだけでなく、対象データの所有者であることをサーバー側で確認する。

---

# 7. タスク管理

## 7.1 タスク一覧

ログインユーザーは、自分のタスク一覧を表示できる。

一覧には少なくとも以下を表示する。

* タスク名
* ステータス
* 優先度
* 期限
* タグ

他ユーザーのタスクは表示しない。

---

## 7.2 タスク登録

ログインユーザーは新しいタスクを登録できる。

登録時に以下を入力できる。

* タイトル
* 詳細
* ステータス
* 優先度
* 期限
* タグ

### 初期値

ステータスを指定しなかった場合は、

```text
TODO
```

とする。

優先度を指定しなかった場合は、

```text
MEDIUM
```

とする。

---

## 7.3 タスク編集

ログインユーザーは自分のタスクを編集できる。

編集対象は以下とする。

* タイトル
* 詳細
* ステータス
* 優先度
* 期限
* タグ

タスクの所有者は変更できない。

---

## 7.4 タスク削除

ログインユーザーは自分のタスクを削除できる。

タスクを削除した場合、そのタスクに関連する `task_tags` も適切に削除する。

他ユーザーのタスクは削除できない。

---

# 8. タスクステータス

タスクのステータスは以下の3種類とする。

| 値             | 表示  |
| ------------- | --- |
| `TODO`        | 未着手 |
| `IN_PROGRESS` | 進行中 |
| `DONE`        | 完了  |

初期バージョンでは上記以外のステータスを使用しない。

---

# 9. タスク優先度

タスクの優先度は以下の3種類とする。

| 値        | 表示 |
| -------- | -- |
| `LOW`    | 低  |
| `MEDIUM` | 中  |
| `HIGH`   | 高  |

初期値は `MEDIUM` とする。

---

# 10. 期限

タスクには期限を設定できる。

期限は任意項目とする。

期限が設定されていないタスクも登録可能とする。

---

# 11. タグ

## 11.1 タグ登録

ユーザーは自分のタグを登録できる。

タグ名は必須とする。

同一ユーザーが同じ名前のタグを複数登録することはできない。

異なるユーザーが同じ名前のタグを使用することは許可する。

---

## 11.2 タグ編集

ユーザーは自分のタグ名を変更できる。

---

## 11.3 タグ削除

ユーザーは自分のタグを削除できる。

タグを削除した場合、そのタグとタスクの関連も適切に削除する。

---

# 12. タスクとタグの関連

1つのタスクに複数のタグを設定できる。

1つのタグを複数のタスクに設定できる。

タスクとタグの関連は `task_tags` テーブルで管理する。

同じタスクに同じタグを複数回設定することはできない。

---

# 13. タスク検索・絞り込み

タスク一覧では、以下の条件による絞り込みを実装する。

* タイトル
* ステータス
* 優先度
* タグ
* 期限

検索・絞り込みの詳細なUIは実装時に決定する。

検索対象はログインユーザー自身のタスクに限定する。

---

# 14. バリデーション

ユーザー入力に対してサーバー側でバリデーションを行う。

少なくとも以下を検証する。

### ユーザー

* 必須項目
* ユーザー名の長さ
* メールアドレス形式
* パスワードの条件
* ユーザー名の重複
* メールアドレスの重複

### タスク

* タイトルの必須チェック
* タイトルの最大長
* 詳細の最大長
* ステータスの許可値チェック
* 優先度の許可値チェック
* 期限の形式チェック

### タグ

* タグ名の必須チェック
* タグ名の最大長
* ユーザー内でのタグ名重複チェック

クライアント側の入力制御だけに依存せず、サーバー側でも検証する。

---

# 15. エラー処理

ユーザー入力によるエラーについては、ユーザーが原因を理解できるメッセージを表示する。

認証エラーの場合は、ログイン画面へ適切なエラーメッセージを表示する。

存在しないタスクや、他ユーザーが所有するタスクへのアクセスについては、データの存在を不必要に公開しない。

システム内部の例外情報やスタックトレースをユーザー画面へ直接表示しない。

---

# 16. 画面

初期バージョンでは以下の画面を作成する。

| 画面     | 認証 | 内容          |
| ------ | -- | ----------- |
| ログイン   | 不要 | ログイン        |
| ユーザー登録 | 不要 | アカウント登録     |
| タスク一覧  | 必須 | 自分のタスク一覧・検索 |
| タスク登録  | 必須 | タスク登録       |
| タスク編集  | 必須 | タスク編集       |
| タグ管理   | 必須 | タグの登録・編集・削除 |

画面デザインはシンプルで操作しやすい構成とする。

---

# 17. REST API

初期バージョンでは、画面表示を主目的としたSpring MVCによるWebアプリケーションとして実装する。

ただし、将来的な外部アプリケーションやAPI連携を考慮し、Service層とController層を適切に分離する。

将来的にはREST APIを追加し、以下のような操作をAPIとして提供できる構成を目指す。

* タスク一覧取得
* タスク取得
* タスク登録
* タスク更新
* タスク削除

初期バージョンでは、REST APIの公開を必須要件とはしない。

---

# 18. Slack API連携

Slack APIを利用したタスク通知機能を将来的に追加する。

初期バージョンではSlack連携を実装しない。

将来的な機能候補として以下を想定する。

* タスク期限の通知
* タスク完了通知
* タスク作成通知
* Slackからのタスク情報確認
* Slackからのタスク操作

Slack APIの認証方式、通知条件、通知先などは、Slack連携を実装する段階で別途要件を定義する。

初期バージョンのDB設計では、Slack連携のためだけにテーブルを追加しない。

---

# 19. 非機能要件

## 19.1 セキュリティ

* パスワードを平文で保存しない。
* Spring Securityを使用する。
* 認証が必要な画面を適切に保護する。
* ユーザーごとのデータ所有権をサーバー側で確認する。
* CSRF対策など、Spring Securityが提供する標準的なセキュリティ機能を適切に利用する。
* DB接続情報などの機密情報をソースコードへ直接記述しない。

## 19.2 データ整合性

* 主キーを適切に設定する。
* 外部キーによってテーブル間の参照整合性を維持する。
* アプリケーション側のチェックだけに依存せず、DB側でも必要な制約を設定する。

## 19.3 保守性

Controller、Service、Repositoryなどの責務を分離する。

DBアクセス処理をControllerへ直接記述しない。

認証・認可処理を各Controllerへ重複して実装しない。

---

# 20. 初期バージョンの対象範囲

初期バージョンでは以下を実装対象とする。

```text
ユーザー登録
    ↓
ログイン
    ↓
タスク一覧
    ├── 検索・絞り込み
    ├── 登録
    ├── 編集
    └── 削除

タグ管理
    ├── 登録
    ├── 編集
    └── 削除

ログアウト
```

以下は初期バージョンでは実装しない。

```text
Slack API連携
外部OAuthログイン
REST APIの外部公開
メール通知
複雑な権限管理
```

これらは初期バージョン完成後の拡張候補とする。

---

# 21. データベース

初期バージョンでは以下の4テーブルを使用する。

```text
users
tasks
tags
task_tags
```

詳細なテーブル定義は `docs/database.md` に記載する。

アプリケーション実装時は `database.md` の定義を基準とし、実装上の都合だけでDB構造を変更しない。

---

# 22. 実装方針

初期バージョンでは、まずWeb画面から一連のタスク管理機能を利用できる状態を完成させる。

実装順序の目安は以下とする。

1. Spring Bootの基本構成
2. PostgreSQL接続
3. Entity / Repository
4. ユーザー登録
5. Spring Securityによるログイン・ログアウト
6. タスクCRUD
7. タグCRUD
8. タスクとタグの関連付け
9. タスク検索・絞り込み
10. バリデーション・エラー処理
11. UI改善
12. テスト

実装中に要件変更が必要になった場合は、既存仕様を勝手に変更せず、変更内容を明示したうえで対応する。
